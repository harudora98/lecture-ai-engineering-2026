- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  - `app/retrieval.py`：`expand_neighbors()` と `search_with_neighbors()` を追加。`load_pages()` のページ順を使い、ヒットしたページの前後 `window` ページを**同じ `document_id` の中だけ**から探して付ける。`page_id` で重複を除き、検索で直接ヒットしたページは前後ページとして先取りせず検索順位の位置に置く。追加ページには `retrieved_by: "neighbor"`、`neighbor_of`（元のページID）、`distance: None` を付け、ヒットには `retrieved_by: "search"` を付けて、モデルが「検索で当たったページ」と「隣だから付いたページ」を区別できるようにした。`python -m app.retrieval --neighbors 1 "..."` で検索だけ確認できる。
  - `app/config.py`：`RAG_NEIGHBOR_PAGES = int(os.getenv("AIE_RAG_NEIGHBORS", "0"))` を追加。既定0なら従来どおり。
  - `app/tools.py`：`search_materials` は `RAG_NEIGHBOR_PAGES > 0` のときだけ `search_with_neighbors` を使う。**docstringは変えていない**（比較条件をそろえるため）。
  - `tests/test_retrieval_neighbors.py`：APIを呼ばずに、前後追加・資料の境界をまたがない・重複しない・先頭/末尾ページ・window=0 を確認するテストを追加（`uv run pytest -q` で 26 passed）。
  - 比較用スクリプトと生ログ：`lectures/05/hw_runs/`（`compare_retrieval.py`、`run_agent_compare.sh`、各実行の `--trace` 出力）。
  - 本文や埋め込み設定は変えていないので、索引は作り直していない（同梱の `index.sqlite3` を使用）。

- 改善した例と、残る失敗・制約：
  - **根拠が増えた例**：Q2。ヒットしたp.36（例題の導入）の次ページp.37が工程の全体図で、まさに質問の答えの骨格だった。スライドは「導入ページ→中身のページ」と続くことが多いので、前後ページ付与と相性が良い。
  - **不要な情報が増えた例**：Q3とQ1。1ページで答えが決まる質問では、付いた前後ページはほぼ全部ノイズで、回答は変わらずトークンと費用だけ増えた。Q3では第1回p.13の隣のHugging Faceのページまで付いた。
  - **残る失敗**：Q2の前後付きでは、モデルが1回の検索で満足して追加検索をしなくなり、データ収集・モデル学習の部分はp.37の短い箇条書きだけで答えた。run1では「講義資料、過去の質問と回答の履歴、FAQなど」のように**出典の付かない一般知識での穴埋め**が出た。一方、通常検索のrun2は3回検索してp.44・p.45・p.47・p.53まで取り、データ収集の具体的なコツ（まず3日で集められるデータで作る等）まで答えていた。つまり「前後ページで根拠は増えたが、モデルが探索をやめてしまい、詳しさでは通常検索の方が良い回もあった」。
  - 制約：各条件2回ずつ・質問3つだけなので、差が偶然の可能性はある。前後ページは近いページほど関連するという前提に頼っていて、章の切れ目（例：Q3のp.21 autoresearch→p.22 Part 4）や補足ページの並びでは外れる。

- 気づき・疑問：
  - 前後ページの付与は「入口のページは当たるが、中身が次のページにある」質問には効くが、ピンポイントの質問では入力トークンが1.7〜2.5倍、推定費用が1.5〜1.9倍になるだけだった。常にONにするより、上位1〜2件だけに付ける、距離がしきい値より近いヒットだけに付ける、章の境界をまたがない、などの条件付きにする方が良さそう。
  - 根拠が増えると、モデルが追加検索をしなくなることがある（Q2）。「根拠を増やす」ことが「探索を減らす」方向に働くのは予想外だった。INSTRUCTIONSで「工程ごとに根拠が足りなければ検索を分ける」と促すとどうなるかは試していない。
  - 同じ入力・出力トークンでも推定費用がrun1とrun2で違った（Q2前後付き 4,463/701 で 0.003091 と 0.002540、Q3前後付き 6,012 で 0.002451 と 0.001916）。`usage` の内訳を表示するスクリプトでQ3前後付きをもう2回実行して確かめると（`hw_runs/usage_detail_q3_nb1.txt`）、どちらも入力6,012のうち2,030トークンが `cache_read`（Geminiの暗黙キャッシュ）になっていて、費用は0.0019055 / 0.0018230 USDとrun2に近かった。run1の高い方はキャッシュが効かなかった回だと考えられる（run1の内訳は記録していないので推測）。比較するときは、キャッシュが効いたかどうかも条件として記録した方がよい。
  - `[cost]` には質問の埋め込みの費用は含まれない。前後付きは埋め込み回数を増やさないので、この点では費用は変わらない（検索回数が減ったQ2ではむしろ埋め込みも減る）。
